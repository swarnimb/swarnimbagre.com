# OpenClaw Configuration: swarnimbagre.com

**Date:** 2026-05-14
**Status:** Spec only. Implementation lives in Phase 3 T30 (the `stats-ingest` Edge Function itself) and T31 (integration test + final doc pass). T29 establishes the shared secret and this doc; the Edge Function code does not yet exist.

This document is the operational spec for the shared-secret authentication that gates the `stats-ingest` Edge Function. It satisfies DS-02 — the secret and its lifecycle are documented before the function that consumes it is written. OpenClaw is a Telegram-bot ingestion agent (Python, runs on a separate machine, separate repository). It is the only party authorized to write to the `stats` table (CONSTRAINT-04), and it does so by including the shared secret in an HTTP header on every request.

Out of scope: the Edge Function code itself (T30), monitoring and alerting on auth failures (T31 — `docs/monitoring.md`), and rate limiting (placeholder hook in T30, no enforcement in Phase 3 — see `docs/architecture.md` §3.3).

---

## 1. Auth Model Summary

- One shared secret, one consumer. The secret is held by exactly two parties: the Supabase Edge Function runtime (as env var `STATS_INGEST_SECRET`) and the OpenClaw runtime (as its own env var, set on the OpenClaw machine).
- Constant-time comparison, mandatory. The function compares the incoming header to the env var using `crypto.timingSafeEqual` to defeat timing oracles (SEC-04).
- INSERT-only blast radius. The Edge Function uses the service role key internally but only ever calls `INSERT INTO stats`. UPDATE, DELETE, and any other table are not reachable through this surface (CONSTRAINT-04, CONSTRAINT-08).
- No alternative path. There is no anon INSERT policy on `stats`. There is no admin UI for writing stats. If the secret is unavailable, stats cannot be ingested — that is the intended failure mode.

## 2. Secret Generation

The secret is generated **once, locally, on the operator's machine**. It is never generated by the application, never derived from a passphrase, and never transmitted over any channel other than direct paste into the two destinations in Section 3.

**Generation command (canonical):**

```
openssl rand -base64 32
```

This produces a 32-byte (256-bit) random value, base64-encoded, ~44 characters. Output goes to stdout; do not redirect to a file in any tracked directory. Paste the value directly into the two destinations in Section 3, then close the terminal.

**Equivalent commands (acceptable alternatives):**

- `openssl rand -hex 32` — 64-char hex, same entropy.
- `python -c "import secrets; print(secrets.token_urlsafe(32))"` — URL-safe base64, slightly different length.

Any ≥32-byte cryptographic random value is acceptable. Do not use `Math.random`, `uuidgen`, password generators, or anything that derives from human-typed input.

**Why ≥32 bytes:** 256 bits of entropy is the floor for symmetric secrets per modern guidance. Below that the secret becomes brute-forceable within timelines that matter.

## 3. Where the Secret Lives

The secret is stored in exactly two locations. Both are env-var slots on running infrastructure. Nothing on disk, nothing in version control (SEC-01, SEC-07).

| Location | Owner | Var name | Set via | Visibility |
|---|---|---|---|---|
| Supabase Edge Function runtime | This project (swarnimbagre.com) | `STATS_INGEST_SECRET` | Supabase dashboard → Edge Functions → Manage secrets, OR `supabase secrets set STATS_INGEST_SECRET=...` via the Supabase CLI | Server-only. Never sent to the browser, never logged. |
| OpenClaw runtime | OpenClaw repository (separate machine, separate repo) | `STATS_INGEST_SECRET` (recommend same name for symmetry) | OpenClaw's own deployment mechanism — typically `.env` on the host machine, gitignored | Process-only on the OpenClaw host. |

**Storage non-locations** (the secret must never appear here):

- The swarnimbagre.com repository, in any committed file. `.env.local` and `.env*` are gitignored (SEC-07); a leaked `.env.example` value would be a defect.
- The OpenClaw repository, in any committed file.
- Vercel environment variables. Vercel runs the Next.js app, which has no need for this secret — only the Supabase Edge Function does. Adding it to Vercel widens the leak surface for no gain.
- Any log line, error message, or HTTP response body (SEC-05). The Edge Function returns 401 with no detail on auth failure; it never echoes the received header.

## 4. OpenClaw-Side Configuration

The OpenClaw bot, when ingesting a stat, sends:

```
POST https://{project-ref}.supabase.co/functions/v1/stats-ingest
X-Stats-Secret: {value of STATS_INGEST_SECRET}
Content-Type: application/json

{"category": "...", "label": "...", "value": "...", "unit": "..." | null}
```

The exact `{project-ref}` and the request body schema come from `docs/architecture.md` §3.3. The endpoint URL is captured in OpenClaw's config alongside the secret. Both are deployment-time config; neither is hard-coded in OpenClaw source.

OpenClaw expects 201 on success and treats 401 as a fatal config error (rotate-then-retry, not retry-loop). 400 is treated as a bot bug (malformed body) and surfaces to the operator. Any 5xx is retried with backoff per OpenClaw's own retry policy (defined in the OpenClaw repo, not here).

## 5. Rotation Procedure

Rotation is needed in three cases: scheduled (none currently scheduled — single-user, low-traffic, low-risk), suspected leak (Section 6), or staff change (not applicable — single operator).

The procedure accepts a brief auth-failure window because there is no atomic two-place write. OpenClaw will see 401s for the seconds-to-minutes between the Supabase rotation taking effect and the OpenClaw env being updated. This is acceptable for a stat ingestion path — stats are not time-critical and OpenClaw's retry policy absorbs the gap.

**Steps, in order:**

1. **Generate the new secret** per Section 2 on the operator's machine.
2. **Update Supabase first.** Set `STATS_INGEST_SECRET` to the new value via the Supabase dashboard or `supabase secrets set`. Edge Functions pick up new secrets on next invocation — no redeploy needed, but expect a small propagation window (seconds).
3. **Verify the old secret is rejected.** From any machine, send a test POST with the old secret. Expect 401. (See Section 7 for the smoke-test command.)
4. **Update OpenClaw second.** Set `STATS_INGEST_SECRET` to the new value on the OpenClaw host. Restart the OpenClaw process so the new env is picked up.
5. **Verify the new secret is accepted.** Send a test POST with the new secret. Expect 201.
6. **Discard the old secret.** Wipe terminal history if the secret was pasted on the command line. The old value is no longer trusted by either side.

**Order matters.** Rotating OpenClaw first would mean OpenClaw is sending the new secret while Supabase still expects the old one — every request 401s until step 2 lands. Rotating Supabase first means OpenClaw 401s briefly until step 4, which is the smaller and more recoverable failure window.

## 6. Leak Response

A leak is: the secret value appearing in any chat log, screenshot, shoulder-surfed terminal, committed file, public log stream, or any other location outside the two env-var slots in Section 3. If in doubt, treat as leaked.

**Immediate response:**

1. Run the rotation procedure (Section 5) without delay. The leaked secret is dead the moment the new secret lands in Supabase.
2. Scan the `stats` table for the leak window. `SELECT * FROM stats WHERE created_at > '{leak time}' ORDER BY created_at` — any row not attributable to a real OpenClaw ingestion is suspect. Delete suspect rows manually via the admin panel or direct SQL.
3. Audit the leak source. Was it a screenshot? A pasted log? A committed file? Fix the root cause — rotation alone does not prevent the next leak from the same source.

There is no automated detection. The leak vector is mitigated by keeping the secret in env-var slots only, never on disk in a tracked directory, and never logged.

## 7. Verification (Smoke Tests)

These are operator-run sanity checks, not automated tests. T31 will add an automated integration test.

**Test that a missing secret is rejected (expect 401):**

```
curl -i -X POST https://{project-ref}.supabase.co/functions/v1/stats-ingest \
  -H "Content-Type: application/json" \
  -d '{"category":"test","label":"smoke","value":"1","unit":null}'
```

**Test that a wrong secret is rejected (expect 401):**

```
curl -i -X POST https://{project-ref}.supabase.co/functions/v1/stats-ingest \
  -H "Content-Type: application/json" \
  -H "X-Stats-Secret: definitely-not-the-real-secret" \
  -d '{"category":"test","label":"smoke","value":"1","unit":null}'
```

**Test that the correct secret is accepted (expect 201):**

Run from a shell where `STATS_INGEST_SECRET` is exported. Do not paste the secret into a curl command on a shared machine.

```
curl -i -X POST https://{project-ref}.supabase.co/functions/v1/stats-ingest \
  -H "Content-Type: application/json" \
  -H "X-Stats-Secret: $STATS_INGEST_SECRET" \
  -d '{"category":"test","label":"smoke","value":"1","unit":null}'
```

After a successful 201, delete the smoke-test row via the admin panel or `DELETE FROM stats WHERE label = 'smoke'`. T30 acceptance includes wiring the function; T31 acceptance includes confirming OpenClaw → Supabase end-to-end.
